## 一、CRITICAL — 正式資料庫有可登入的 admin 後門

**發現**:正式 DB(`/srv/sites/flyingchess/database.sqlite`)裡的 `admin@admin.com`,密碼就是 `admin1234`(對真實 bcrypt hash 直接 `password_verify` 通過)。這是 `DevAccountSeeder` 的開發種子帳號 —— 種子檔本身有 `app()->environment('local','testing')` 防護,問題出在 **dev/prod 共用同一份 SQLite**,在非 production 環境跑了 seeder,線上這份檔就中了。任何人都能用這組帳密進 `/admin` 全面管理。

**修復**:把 `admin@admin.com` 的密碼改成亂數、`is_admin=0`(非破壞性,不動它名下的 10 筆遊戲紀錄)。已驗證 `admin1234` 現在被拒。
**待你確認**:第三個 admin `fiy.mify@gmail.com`(未驗證、無資料、非弱密碼)保留未動 —— 若不是你本人/協作者請刪。
**根因提醒**:不要對正式 DB 跑 `db:seed`;dev 請用獨立的 sqlite 檔。

## 二、HIGH — Host header 注入(密碼重設連結投毒)

**發現**:origin(nginx)直接接受任意 `Host` 標頭並反射進 canonical、表單 action、以及**密碼重設信的連結**。從 origin IP 走純 HTTP 可繞過 Cloudflare。實測 `Host: evil.example.com` → 整頁連結都變成 evil 網域;攻擊者對某帳號觸發密碼重設,信裡的重設連結就指向他的釣魚站。

**修復**:`bootstrap/app.php` 加 `trustHosts()`,只信任 `pillownight.com`(含子網域)、preview 的 nip.io、localhost。Host 對不上的請求直接 400,連控制器都到不了。⚠ 這些值是正規表達式,已錨定 `^...$` 並跳脫點號(否則 `pillownight.com` 會變成鬆散樣式)。實測 evil host → 400、正式/preview host → 200。
**檔案**:`bootstrap/app.php`

## 三、HIGH — SNS webhook 可被任意 AWS 帳號偽造 → 封鎖任意信箱

**發現**:`/ses/feedback`(公開、免 CSRF)驗簽正確,但**從不檢查 TopicArn**。攻擊者在自己的 AWS 帳號建一個 SNS Topic、把我們的端點訂進去,發出來的通知一樣簽章合法 → 可把**任意 email 加進寄信抑制清單**,使該帳號永久收不到信(含密碼重設、email 驗證)。而且原本**沒有任何解除抑制的路徑**。

**修復**:
- `SnsMessage::isValid()` 加 TopicArn 白名單(`hash_equals` 比對 `config('services.ses.topic_arn')`)。未設定時 **fail-closed(全部拒收)**,並把該訊息真實 ARN 記進 log —— 這樣不必事先知道 ARN 就能安全上線。
- 兩處對外 HTTP 加 `withoutRedirecting()`,避免主機白名單只驗第一跳被轉址繞過(SSRF)。
- 新增解除抑制指令:`php artisan mail:unsuppress {email}`。
- 新增 2 條測試(錯誤 Topic 被拒、未設定時拒收)。
**⚠ 待你設定**:`.env` 的 `SNS_TOPIC_ARN=` 目前留空,退信通知會被拒收。等下一則真實通知把 ARN 寫進 `storage/logs/laravel.log`,貼進 .env 即恢復。
**檔案**:`app/Support/SnsMessage.php`、`app/Http/Controllers/SesFeedbackController.php`(不變)、`app/Models/EmailSuppression.php`、`app/Console/Commands/UnsuppressEmail.php`、`config/services.php`、`.env(.example)`、`tests/Feature/EmailSuppressionTest.php`

## 四、HIGH — Truth-Dare `tab_id` 無上限 → 磁碟填爆 DoS

**發現**:`TruthDareController::playerSessionId()` 把使用者可控的 `tab_id` 未驗證、原封不動串接寫進 `game_players.session_id`(對照 `GameController` 有 hash 成 64 字元)。SQLite TEXT 欄位不限長度 + 該路由無 throttle → 一次請求可寫約 18MB,約 2000 次塞爆磁碟(SQLite/session/cache 一起死)。

**修復**:比照 `GameController`,把 `tab_id` 先 `hash('sha256', ...)` 成固定 64 字元。
**檔案**:`app/Http/Controllers/TruthDareController.php`

## 五、HIGH — 遊戲/清單端點幾乎無限速

**發現**:`games` 與 `truth-dare` 的 create/join/start/roll/move/draw、bucket-list/time-capsule 的寫入端點都沒 throttle。後果:(1) 6 個 FPM worker + 單寫 SQLite,少量並發 roll/move/draw 即可癱瘓全站;(2) Truth-Dare `draw` 連抽即可枚舉整份題庫。

**修復**:對各端點加合理 throttle —— 對戰類 roll/move `90/分`、draw `40/分`、create/join `20/分`、清單寫入 `30/分`、state 輪詢 `120/分`。對真人非常寬鬆,對腳本是硬牆。
**檔案**:`routes/web.php`

## 六、HIGH — 後台會員頁 Stored XSS

**發現**:註冊暱稱 `$user->name` 無過濾,被渲染進 `onsubmit="return confirm('…「{{ $user->name }}」…')"`。HTML 屬性會把 `&#039;` 解碼回單引號 → 跳出 JS 字串執行任意程式碼。觸發點是 admin 點「封鎖/刪除」時,在 **admin 的 session、admin 的來源**上執行,可挾持 CSRF token 打任意後台動作。

**修復**:把暱稱從 JS 字串字面搬到 `data-confirm` 屬性,改用 `onsubmit="return confirm(this.dataset.confirm)"` —— `{{ }}` 在屬性內會跳脫引號,`dataset` 以純字串讀取,永不再被當程式碼解析。另加縱深防禦:註冊暱稱 `regex:/^[^<>]+$/` 擋角括號(撇號等合法字元不擋)。
**檔案**:`resources/views/admin/users/index.blade.php`、`resources/views/admin/users/edit.blade.php`、`app/Http/Controllers/AuthController.php`

## 七、MEDIUM — 願望清單/時光膠囊的 partner 身分被「開頁」自動搶走

**發現**:`resolveRole()` 只要 `partner_token` 還是 null 就把開頁者當 partner-new,`show()`(GET)隨即寫入 token。後果:(1) 任何拿到分享連結的人先開先得,永久佔走 partner;(2) 更糟 —— 連結預覽 bot(Facebook/Twitter/ChatGPT-User 等,都被放行過年齡閘)一抓就把 partner 燒掉,真正的另一半被鎖成唯讀。等於「把連結貼進聊天室」這個動作本身就會弄壞功能。

**修復**:改成明確認領 —— 新增 `POST /{code}/claim`(CSRF + throttle),頁面顯示「我是另一半,加入」按鈕,只有使用者主動送出才發 token。`resolveRole()` 不再自動回 partner-new。bot 不會 POST,所以碰不到。另補 time-capsule `saveAnswers` 的陣列大小與長度上限(擋 20MB JSON body 卡 worker)。
**檔案**:`app/Http/Controllers/BucketListController.php`、`app/Http/Controllers/TimeCapsuleController.php`、兩個 `show.blade.php`、`routes/web.php`、`lang/*/games.php`、`lang/*/minigame.php`、`public/css/minigames.css`

## 十、防止網站被複製(anti-copy)

先說結論:**公開的 SSR 站無法被完全「防複製」** —— 內容必須可被搜尋引擎檢索才有 SEO,能被 Google 讀到的東西就能被人抓。能做的是讓「整站打包」變貴、確保被抄的內容仍指回你、擋掉最省事的路徑。已做與建議如下:

**已在程式層做的:**
- 擋掉專門的整站離線複製工具 UA(HTTrack / Teleport / Offline Explorer / WebCopier / Scrapy / …),直接回 403。刻意**不擋** curl/wget/python 這類泛用客戶端(有正當用途:健康檢查、連結預覽、你自己的腳本,擋了誤傷大又防不到決心複製的人)。`app/Http/Middleware/AgeVerification.php`
- 訓練型 AI 爬蟲已在 robots.txt + 年齡閘雙重封鎖(既有)。
- `trustHosts` 讓別人無法用你的 origin 以他們的網域對外服務你的內容;canonical 一律指回 pillownight.com,被整頁複製時 Google 會把原創歸給你。

**強烈建議在 Cloudflare 做(比程式層有效得多,你已經在用 CF):**
- **Bot Fight Mode / Super Bot Fight Mode**:用 JA3/行為特徵擋自動化流量,不是只看 UA 字串。
- **Scrape Shield**(含 Email Obfuscation、Hotlink Protection):擋圖片熱連結與 email 收割。
- **Rate Limiting Rules**:對「每 IP 每分鐘抓幾頁」設上限,直接在邊緣擋住大規模鏡像。
- **WAF Managed Rules**:擋常見掃描與爬蟲樣式。

這四項在 CF 後台開關即可,是「防複製」投報率最高的地方。

### § Cloudflare 設定 runbook(2026-08-20 補)

#### ⚠️ 先看這兩個雷,再動任何開關

**1. Bot Fight Mode 可能把 AI 檢索爬蟲一起擋掉。** 這站刻意分兩類處理
(見 `tests/Feature/GenerativeEngineAccessTest.php`):

| 類別 | 爬蟲 | 站上的處置 |
|---|---|---|
| 檢索型(會把我們列進答案) | OAI-SearchBot、PerplexityBot | **放行到真實頁面** |
| 訓練型(只是拿去訓練) | GPTBot、ClaudeBot | 給年齡閘 |

Bot Fight Mode 是靠行為特徵擋自動化流量,它認的是 CF 自己的 verified bots 清單 ——
檢索型 AI 爬蟲不一定在裡面。開下去有機會把「被 AI 搜尋引擎引用」這條流量整條掐掉,
而那是這站少數不受 SafeSearch 影響的曝光來源。**所以它要排最後做,而且開完立刻驗。**

**2. 「Block AI bots / AI Scrapers and Crawlers」那個一鍵開關絕對不要開。** 它會連
檢索型一起擋。這站的立場是「訓練型擋、檢索型放」,那是靠 robots.txt 與年齡閘做的
分流,不是靠 CF 的一鍵開關。

#### 建議的順序(低風險 → 高風險)

**第一步:WAF Managed Rules(免費方案的 Free Managed Ruleset)。** 擋常見掃描樣式,
幾乎不會誤傷真人。直接開。

**第二步:Scrape Shield。**
- Email Obfuscation:開。站上沒有公開 email,但成本是零。
- Hotlink Protection:**保留評估**。它會擋掉帶外部 Referer 的圖片請求,而社群平台
  抓 og:image 通常不帶 Referer(所以多半沒事)—— 但分享預覽圖是這站的流量入口之一,
  開之前先手動確認 Facebook / Twitter 的分享除錯工具還抓得到圖。

**第三步:Rate Limiting Rules。** 免費方案給一條規則,拿來擋整站鏡像:

```
表達式:  (not http.request.uri.path matches "^/(css|js|img|fonts)/")
        and (not http.request.uri.path in {"/robots.txt" "/ads.txt" "/sitemap.xml"})
門檻:    每 1 分鐘 100 次請求(同一 IP)
動作:    Managed Challenge(不要用 Block)
期間:    1 分鐘
```

為什麼是這些值:真人快速瀏覽大約 20–30 次/分鐘(靜態資源被排除且多半有快取),
`wget -r` 這種整站抓取是好幾百次/分鐘。100 次留了三倍以上的餘裕。動作選
Managed Challenge 而不是 Block —— 誤判時真人還過得去,Block 就是直接白畫面。

排除靜態路徑是必要的:一個頁面會帶好幾個 css/js 請求,不排除的話門檻等於被除以五。

**第四步(最後):Bot Fight Mode。** 開之前先跑下面的驗證指令留一份基準,開完馬上
再跑一次比對。如果檢索型爬蟲從 200 變成 403 / challenge,就關掉 —— 對這站來說
AI 檢索的曝光比多擋掉一些鏡像更值錢。

Pro 方案的 Super Bot Fight Mode 可以把 "Verified bots" 設成 Allow、只擋
"Definitely automated",誤傷小得多。免費方案沒有這個細分。

#### 每改一項之後的驗證

```bash
# 檢索型 AI 爬蟲:必須是 200 且看得到真實內容
for ua in "Mozilla/5.0 (compatible; OAI-SearchBot/1.0; +https://openai.com/searchbot)" \
          "Mozilla/5.0 (compatible; PerplexityBot/1.0; +https://perplexity.ai/perplexitybot)" \
          "Googlebot/2.1 (+http://www.google.com/bot.html)"; do
  printf '%s → %s\n' "${ua:0:30}" \
    "$(curl -s -o /dev/null -w '%{http_code}' -A "$ua" https://pillownight.com/tw)"
done

# sitemap 與 robots 不能被擋(它們在 rate limit 的排除清單裡)
curl -s -o /dev/null -w 'sitemap %{http_code}\n' https://pillownight.com/sitemap.xml
curl -s -o /dev/null -w 'robots  %{http_code}\n' https://pillownight.com/robots.txt
```

三個都要是 200。任何一個變成 403 或 503,就是上一項設定誤傷了 —— 回頭關掉那一項,
不要「先放著看看」,被擋的期間 Google 會直接降低爬取速率。

#### 程式端已經有的部分(不用重複做)

- 每頁的節流:迷你遊戲頁 40 次/分鐘(具名節流器,見 `AppServiceProvider`),
  題庫送出去的量本身也裁切過(`App\Support\ContentExposure`)
- robots.txt 由程式產生,擋掉 admin / boards / profile / 密碼相關路徑
- 年齡閘對寫入型請求連爬蟲一起擋

CF 的規則是**邊緣**那一層,和上面這些不重複 —— 程式端擋的是「一直重載同一頁撈題庫」,
CF 擋的是「整站鏡像」。兩層打的是不同的東西。
